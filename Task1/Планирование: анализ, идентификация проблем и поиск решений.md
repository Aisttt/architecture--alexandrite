## 2. Семь ключевых проблем

| № | Проблема                                | Симптомы                                         | Влияние                                     |
|---|-----------------------------------------|--------------------------------------------------|---------------------------------------------|
| 1 | **Пропажа или дубли заказов**           | Статус зависает/исчезает, иногда дубли заказов   | Критическое — прямой удар по деньгам        |
| 2 | **Нет технического мониторинга**        | Узнаём о сбоях из жалоб                          | Высокое — нет видимости системы             |
| 3 | **Длинный расчёт цены (до 30 мин при сложной 3D-модели)** | Таймауты B2B-API                     | Критическое — уходят партнёры               |
| 4 | **Медленный дашборд MES**               | Список заказов грузится 5–10 с                   | Среднее — операторы теряют время            |
| 5 | **Единичные инстансы (SPOF)**           | Любой сбой останавливает всю систему             | Критическое                                |
| 6 | **Нет централизованного логирования**   | Часы на ручной сбор логов                        | Высокое — длинный MTTR                      |
| 7 | **Ручные релизы и тесты**               | Месяц на выпуск, внезапные баги                  | Среднее                                     |

## 3. Шаг 0: одноразовый аудит «где заказы потерялись»

1. **Выгружаем** `order_id, status, updated_at` из Shop DB, CRM DB, MES DB (6 мес).  
2. **JOIN** три таблицы → ищем разрывы:  
   * `SUBMITTED` в Shop, **нет** в CRM ⇒ publish Shop / consumer CRM
   * `PRICE_CALCULATED` в CRM, **нет** в MES ⇒ consumer MES или сообщение отброшено в DLQ
   * `MANUFACTURING_STARTED` в MES > 21 день ⇒ процесс оператора
3. **Смотрим RabbitMQ** backlog и DLQ.  
4. Формируем таблицу «точек разрыва» → ясно, что чинить первым.

### Быстрый костыль — вертикальное масштабирование

Если VM/БД **CPU-bound** (CPU > 80 % или I/O-лимит), временно **scale-up** (больше vCPU/RAM).  
Снимает боль (расчёт 30 → 10 мин), но **не решает логические ошибки** и упирается в лимит тарифа.

## 4. Инициативы

| ID  | Что делаем                                                          | Выгода                                                        |
|-----|---------------------------------------------------------------------|---------------------------------------------------------------|
| **M1** | Мониторинг + алерты (Prometheus → Grafana)                         | Ошибки и перегрузки видны за минуты                           |
| **R1** | Надёжная очередь (DLQ, retry, idempotent consumer)                | Заказы не теряются, не дублируются                            |
| **C1** | Асинхронный расчёт цены (worker pool на C# / Java + кеш в Redis TTL 24 ч или запись в БД цены после расчёта) | API не ждёт 30 мин, партнёры довольны |
| **T1** | Трейсинг (OpenTelemetry + Jaeger)                                 | По `orderId` видно, где завис заказ                           |
| **S1** | Кеш горячих данных MES (Redis TTL 60 с для списка заказов, 24 ч — для стоимости) | Дашборд < 200 мс |
| **H1** | Kubernetes + HPA                                                 | Убираем SPOF, авто-масштабируемся                             |
| **L1** | ELK / OpenSearch                                                 | Инцидент = минуты, корреляция по `orderId`                    |
| **D1** | Репликация PostgreSQL (primary + follower, failover) | Устраняем SPOF баз, быстрый recovery |

## 6. Целевая архитектура (Т+6)

* **M1** → метрики & алерты latency / error / queue length  
* **R1** → RabbitMQ с DLQ, retry, idempotency  
* **C1** → worker-pool, 95 % расчётов < 3 с  
* **S1** → Redis-кеш, дашборд MES < 200 мс  
* **T1** → Jaeger-трасса Shop → CRM → MES  
* **H1** → первые сервисы в Managed Kubernetes, auto-scaling и PDB

## 7. Дорожная карта реализации

### 7.1 Детальный план по неделям

#### **Недели 1-2: Экстренная диагностика**
- **W1–W2**: Одноразовый аудит БД → фиксим самые частые провалы
- **Результат**: Понимание точек разрыва, быстрые исправления

#### **Недели 1-4: Базовый мониторинг**
- **W1–W4**: M1 — развёртываем Prometheus + Grafana, подключить alert-канал (Slack / Telegram)
- **Метрики**: Базовые метрики всех сервисов
- **Результат**: Видимость состояния системы

#### **Недели 3-6: Надёжность очередей**
- **W3–W6**: R1 — DLQ, повторная доставка, idempotent‑consumer
- **Результат**: Заказы не теряются при сбоях

#### **Недели 5-8: Производительность**
- **W5–W8**: C1 — вынос расчёта в отдельный worker, кэшируем результат
- **Результат**: B2B API работает быстро и стабильно

#### **Недели 7-10: Трейсинг**
- **W7–W10**: T1 — ставим Jaeger, вшиваем trace‑id, учим поддержку
- **Результат**: Быстрая диагностика проблем с заказами

#### **Недели 9-12: UX операторов**
- **W9–W12**: S1 — кеширование списка заказов в MES (Redis + TTL)
- **Результат**: Быстрый отклик интерфейса MES

### 7.2 Следующие этапы (после W13)
- **H1**: Переход на Kubernetes для масштабируемости
- **L1**: Централизованное логирование для полной наблюдаемости

## 8. Ресурсы и команда

### 8.1 Необходимые роли
- **DevOps инженер** (1 FTE) — мониторинг, K8s, инфраструктура *(если не наймём — сокращаем объём H1/D1, нанимаем аутсорс)*
- **Backend разработчик** (1.5 FTE) — очереди, API, оптимизация *(контингент: при нехватке BE фокус на M1–R1, перенос C1 позже)*
- **Frontend разработчик** (0.5 FTE) — оптимизация MES интерфейса
- **QA / Automation** (0.5 FTE) — тестирование новых решений

### 8.2 Инфраструктурные требования
- **Мониторинг**: Prometheus + Grafana + AlertManager
- **Кеширование**: Redis cluster
- **Очереди**: RabbitMQ с HA конфигурацией
- **Трейсинг**: Jaeger или аналогичное решение

## 9. Риски и митигация

### 9.1 Технические риски
- **Риск**: Падение производительности при внедрении мониторинга
- **Митигация**: Постепенное внедрение, тестирование на staging

- **Риск**: Сложность миграции существующих очередей

- **Риск**: Некорректная оценка TTL кеша → устаревшие данные у операторов
- **Митигация**: Наблюдаем hit/miss и корректируем TTL

- **Риск**: Временное снижение стабильности во время миграции
