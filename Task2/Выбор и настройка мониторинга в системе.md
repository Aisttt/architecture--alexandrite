# Выбор и настройка мониторинга в системе

## 1. Введение
В этом документе описывается план внедрения мониторинга для системы компании «Александрит».

## 2. Мотивация
Мониторинг необходим для:
- обнаружения деградации SLA до того, как о ней узнаёт клиент;
- сокращения MTTR при инцидентах;
- получения данных для планирования мощности инфраструктуры;
- быстрой валидации гипотез об оптимизациях;
- формирования **KPI по SLA** для внутренней отчётности и B2B-контрактов.

## 3. Выбор подхода к мониторингу
| Сегмент | Подход | Почему |
|---------|--------|--------|
| HTTP-API (Shop, CRM, MES) | RED (Rate, Errors, Duration) | Фокус на пользовательских запросах |
| RabbitMQ | USE (Utilisation, Saturation, Errors) | Классический метод для брокеров |
| PostgreSQL / Redis / S3 | «4 золотых сигнала» | latency/traffic/errors/saturation для stateful-компонентов |

## 4. Метрики
| Компонент | Метрика | Зачем | Ярлыки |

## 5. План действий
1. Создать time-series хранилище: YC **Managed Service for Prometheus** с долговременным storage на **VictoriaMetrics**.
2. Развернуть **Prometheus Operator** в Managed Kubernetes (MKS) — получаем автоматический lifecycle Alertmanager / Grafana / ServiceMonitor.
3. Настроить экспортёры:
   - **node_exporter** на всех VM;
   - **kube-state-metrics** и **cadvisor** для метрик контейнеров;
   - **rabbitmq_exporter**;
   - **postgres_exporter**;
   - **Spring Boot Actuator + Micrometer** (Shop/CRM);
   - **OpenTelemetry .NET exporter** (MES).
4. Настроить Grafana дашборды:
   - «RED API»;
   - «RabbitMQ / DLQ»;
   - «DB & Storage Health»;
   - «Golden Signals» one-pager для CTO.
   - «SLA/SLO Burn Rate» дашборд для B2B-контрактов (Grafana).
5. Alertmanager:
   - Каналы: Slack `#alerts`, Telegram on-call, SMS reserve;
   - Шаблоны: latency P95 > 2 s (**5m avg**), DLQ > 0 (imм.), **CPU avg util > 80 % (avg over 5m)**.
   - **Prometheus Operator уже развёртывает Alertmanager; добавим CRD `AlertmanagerConfig` для управления из GitOps.**
6. Подготовить Terraform-код (`infrastructure/monitoring`) для повторяемого развёртывания.
7. Провести воркшоп: «как читать графики, как признавать алерты».

## 6. Показатели насыщенности
| Метрика | Порог | Действие |
|---------|-------|----------|
| CPU Shop API (avg util) | > 80 % (5 мин) | HPA добавляет поды |
| Redis used_memory_ratio | > 75 % (10 мин) | Масштаб Redis Cluster / шардирование |

ПРИМЕЧАНИЕ: пороги основаны на исторических данных, будут корректироваться после первого месяца наблюдений.

## 7. Обоснование для бизнеса
- **Сколько стоит простой 1 часа?** N заказов × средний чек. Мониторинг окупается после первой предотвращённой аварии.
- **SLA-репутация B2B**: метрики подтверждают «99.9 % uptime» → партнёры остаются.
- **Снижение MTTR**: поиск причины инцидента 15 мин вместо 4 ч.
- **Планирование инфраструктуры**: тренды CPU/Billing показывают, когда нужен scale-up, экономя бюджет.
